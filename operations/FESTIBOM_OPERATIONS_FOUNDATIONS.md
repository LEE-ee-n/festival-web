# 페스티봄 서비스 운영 준비 안내서

> 이 문서는 명령어를 모아 둔 운영 매뉴얼이 아니다.
> 서비스 운영에서 무엇이 필요하고, 왜 필요한지, 페스티봄은 현재 어디까지 준비됐는지를 이해하기 위한 선행 문서다.

## 1. 서비스 운영이란 무엇인가

개발은 기능을 만드는 일이고, 운영은 사용자가 그 기능을 계속 안전하게 사용할 수 있도록 유지하는 일이다.

서비스는 배포 후에도 다음 이유로 문제가 생긴다.

- Vercel, Supabase, Google 로그인처럼 외부 서비스가 멈추거나 설정이 바뀐다.
- 코드 수정이 기존 기능을 망가뜨릴 수 있다.
- 운영자가 데이터를 잘못 수정하거나 삭제할 수 있다.
- 계정, 비밀키 또는 관리자 권한이 탈취될 수 있다.
- 데이터와 사용자가 늘면서 속도와 비용이 달라진다.
- 잘못된 축제 정보, 만료된 링크, 이미지 권리 요청이 들어온다.

따라서 운영의 핵심은 문제가 전혀 생기지 않게 만드는 것이 아니다.

1. 문제를 빨리 발견하고
2. 피해가 커지지 않게 막고
3. 정상 상태로 복구하고
4. 같은 문제가 반복되지 않게 기록하는 것이다.

## 2. 페스티봄 운영의 특징

페스티봄은 단순한 소개 홈페이지보다 운영할 것이 많다.

- 축제, 티켓, 라인업, 타임테이블처럼 계속 변경되는 공개 데이터가 있다.
- Google 로그인과 관심 아티스트, 개인 일정, 페스티봄 일기 같은 개인정보가 있다.
- 관리자 화면에서 운영 데이터를 직접 수정한다.
- Vercel, Supabase, Google OAuth, GitHub, GA4, Clarity 등 여러 외부 서비스에 의존한다.
- 포스터, 아티스트 로고, Instagram 정보처럼 출처와 권리 요청을 고려해야 하는 자료가 있다.

즉, 페스티봄 운영은 크게 **기술 운영**, **데이터 운영**, **사용자 운영**으로 나뉜다.

## 3. 반드시 이해해야 할 운영 분야

### 3.1 장애 감지와 알림

**왜 필요한가**

서비스가 고장 나도 운영자가 모르면 사용자가 먼저 발견한다. 로그인만 실패하거나 일기 저장만 실패하는 부분 장애는 홈페이지 첫 화면만 확인해서는 알 수 없다.

**페스티봄에서 생길 수 있는 사례**

- 홈페이지는 열리지만 Supabase 오류로 개인 일정 저장이 안 된다.
- Google OAuth 설정 변경으로 로그인만 실패한다.
- Vercel 배포는 성공했지만 특정 상세페이지에서 500 오류가 발생한다.
- 예약 백업 또는 티켓 알림 Cron이 실패한다.

**현재 필요한 최소 수준**

- 홈페이지 응답 상태 자동 확인
- 브라우저·서버 오류 수집
- 배포 실패, 백업 실패, Cron 실패 알림
- 알림을 받을 이메일 또는 Discord 한 곳 확정
- 알림을 받았을 때 처음 확인할 순서 기록

**나중에 사용자가 많아지면**

- 로그인·저장 같은 핵심 기능의 자동 시나리오 점검
- 응답속도와 오류율 기준 설정
- 공개 상태 페이지와 장애 공지 절차

### 3.2 배포와 변경 관리

**왜 필요한가**

운영 장애의 상당수는 새로운 코드나 DB 변경 직후 발생한다. 무엇을 언제 바꿨는지 알아야 원인을 찾고 이전 상태로 돌아갈 수 있다.

**페스티봄에서 생길 수 있는 사례**

- 화면 수정 후 모바일에서 버튼이 사라진다.
- DB migration과 코드 배포 순서가 어긋나 저장 기능이 실패한다.
- 로컬에서는 정상인데 Vercel 환경변수가 없어 운영에서만 실패한다.

**현재 필요한 최소 수준**

- 수정 전 `git status`로 작업 범위 확인
- 테스트, TypeScript, ESLint, 프로덕션 빌드 통과
- 주요 모바일·PC 화면 직접 확인
- DB 변경 전 백업
- 배포 후 운영 URL에서 로그인·저장·삭제 확인
- 문제가 생겼을 때 되돌릴 커밋과 DB 대응 방법 기록

**중요한 구분**

- 코드 롤백은 Git/Vercel로 비교적 쉽다.
- 이미 실행한 DB migration과 삭제된 데이터는 코드 롤백만으로 돌아오지 않는다.
- 따라서 DB 변경은 코드보다 더 신중하게 백업과 복구 방법을 먼저 정해야 한다.

### 3.3 백업과 복구

**왜 필요한가**

백업은 파일을 만드는 작업이고, 복구는 그 파일로 서비스를 되살리는 작업이다. 백업 파일이 있어도 열리지 않거나 필요한 항목이 빠졌다면 실제 사고에서는 쓸 수 없다.

**페스티봄의 현재 상태**

- Windows 작업 스케줄러에서 Supabase `public` schema와 데이터를 매일 백업한다.
- 파일 크기와 SHA-256 무결성을 확인한다.
- 현재 백업에는 Supabase Auth 사용자, Storage 실제 이미지, 프로젝트 설정·비밀값이 포함되지 않는다.
- 컴퓨터가 켜지고 로그인되어 있으며 Docker를 실행할 수 있어야 예약 백업이 동작한다.

**아직 필요한 것**

- 최신 백업을 별도 테스트 환경에 실제 복원
- 테이블 행 수, 관계, 로그인 연결, 핵심 화면 확인
- Storage 이미지 별도 백업 방법 결정
- 백업을 같은 컴퓨터 밖의 Drive 또는 외장 저장소에도 복사
- 최근 4주 보관과 오래된 백업 삭제가 실제로 지켜지는지 확인

**알아둘 용어**

- RPO: 사고가 났을 때 최대 얼마 전 데이터까지 잃어도 되는가
- RTO: 사고 후 서비스를 몇 시간 안에 복구해야 하는가

초기 페스티봄은 예를 들어 “최대 하루 데이터 손실, 하루 안에 복구”처럼 현실적인 기준부터 정할 수 있다. 수치는 실제 복구 시험 후 확정한다.

### 3.4 보안과 권한

**왜 필요한가**

개인 서비스는 한 사용자가 다른 사용자의 일정과 일기를 보거나 수정할 수 없어야 한다. 관리자 계정이 탈취되면 전체 축제 데이터가 변경될 수 있다.

**현재 준비된 것**

- 관리자 1명 제한
- 관리자 TOTP MFA와 `aal2` 강제
- 일반 사용자의 관리자 화면·RPC 접근 차단
- 사용자 간 개인 데이터 RLS 교차 접근 거부 시험
- 회원탈퇴와 개인 데이터 삭제 검증
- 비밀키를 Git과 브라우저 코드에 넣지 않는 구조
- 기본 HTTP 보안 헤더와 CSP 관찰 설정

**계속 운영해야 하는 것**

- GitHub, Vercel, Supabase, Google 계정 모두 2단계 인증 유지
- 복구 이메일·전화번호와 복구 코드 안전 보관
- 사용하지 않는 키와 세션 폐기
- Supabase Security Advisor와 의존성 취약점 정기 확인
- 관리자 권한과 Bot 권한이 늘어나지 않았는지 점검
- 사고가 의심되면 증거를 지우기 전에 계정·키·로그를 보존

### 3.5 개인정보와 사용자 요청

**왜 필요한가**

페스티봄은 이메일, 로그인 식별정보, 관심 아티스트, 개인 일정과 일기를 처리한다. 실제 기능과 개인정보처리방침이 다르면 문제가 된다.

**현재 준비된 것**

- Google 로그인과 개인 기능을 반영한 개인정보처리방침
- 분석 허용을 선택한 경우에만 GA4·Clarity 실행
- 회원탈퇴와 개인 데이터 삭제
- 개인 데이터 보유·백업 잔존 기준 문서화

**운영 중 필요한 것**

- 문의·오정보·삭제·개인정보 요청 접수 채널 하나 유지
- 접수일, 요청 내용, 처리자, 완료일을 최소한으로 기록
- 탈퇴·삭제 요청 처리 결과 확인
- 외부 서비스나 보유기간이 바뀌면 처리방침도 함께 수정
- 개인정보가 포함된 문의 내용을 불필요하게 다른 문서에 복사하지 않기

### 3.6 축제·아티스트 데이터 품질

**왜 필요한가**

페스티봄의 신뢰도는 화면 디자인보다 일정과 라인업이 정확한지에 크게 좌우된다. 잘못된 시간 하나가 사용자의 현장 계획에 직접 영향을 준다.

**운영 기준으로 필요한 것**

- 데이터마다 가능하면 공식 출처 URL과 확인일 기록
- 신규, 수정, 취소, 종료 상태를 구분
- 축제 날짜·지역·공연 시간 검증
- 시간 미발표와 실제 누락을 구분
- 중복 축제·아티스트 병합 기준 유지
- 티켓·Instagram·공식 홈페이지 링크 만료 확인
- 잘못된 정보 제보가 들어오면 수정 전 원본과 출처 비교

**권리 관리가 필요한 자료**

- 축제 포스터와 썸네일
- 아티스트 로고
- Instagram에서 가져온 이미지
- 티켓 판매처의 설명과 이미지

최소한 `출처`, `사용 형태`, `삭제 요청 여부`, `확인일`을 기록한 대장이 필요하다.

### 3.7 외부 서비스 계정과 비용

**왜 필요한가**

페스티봄 코드는 정상이어도 Vercel, Supabase 또는 도메인 결제 실패로 서비스가 중단될 수 있다. 무료 플랜 한도를 넘으면 예상하지 못한 제한도 생길 수 있다.

**관리할 항목**

- 도메인 등록 업체와 만료일
- Vercel 프로젝트와 사용량
- Supabase DB·Auth·Storage·함수 사용량
- Google OAuth 프로젝트
- GitHub 저장소와 관리자 권한
- GA4·Clarity 속성
- 운영 이메일과 복구 수단

각 서비스에 대해 `로그인 계정`, `용도`, `결제·만료`, `2단계 인증`, `복구 방법`만 기록하고, 비밀번호와 비밀키 자체는 비밀번호 관리자에 저장한다.

## 5. 혼자 운영할 때 특히 조심할 점

혼자 운영하면 의사결정은 빠르지만 다음 위험이 있다.

- 운영자 컴퓨터가 고장 나면 백업과 작업 방법을 동시에 잃는다.
- 본인만 아는 계정이나 설정은 시간이 지난 뒤 본인도 기억하기 어렵다.
- 장애 중 급하게 여러 설정을 바꾸면 원인을 찾기 어려워진다.
- 개발과 데이터 수정과 고객 문의를 동시에 처리하면 기록이 빠지기 쉽다.

그래서 작은 서비스일수록 거대한 시스템보다 다음 네 가지가 효과적이다.

1. 체크리스트
2. 변경 기록
3. 다른 장소의 백업
4. 실제 복구 연습

## 6. 현실적인 운영 주기

### 매일 또는 데이터 작업일

- 홈페이지와 로그인 이상 여부 확인
- 오류·배포·백업 실패 알림 확인
- 신규 축제와 변경 정보 검수
- 관리자 작업 전 대상과 출처 확인

### 매주

- 최신 백업 성공과 파일 크기 확인
- 주요 기능 한 번씩 직접 시험
- 사용자 문의·오정보·삭제 요청 확인
- Vercel·Supabase 사용량과 오류 추세 확인

### 매월

- 외부 계정과 2단계 인증·복구 수단 확인
- 의존성 보안 감사
- 오래된 백업과 로그 보관기간 정리
- 개인정보처리방침과 실제 기능 차이 확인
- 축제·이미지 출처 대장 누락 확인
- 비용과 무료 한도 확인

### 배포할 때마다

- 변경 범위 확인
- 자동 검사와 모바일·PC 점검
- DB 변경 전 백업
- 배포 직후 운영 URL 점검
- 이상 시 추가 수정보다 먼저 원인과 되돌릴 기준 결정

### 장애가 발생했을 때

- 발견 시각과 증상 기록
- 무관한 배포·DB 작업 중지
- 영향 범위와 최근 변경 확인
- 필요한 계정·키·경로만 차단
- 복구 후 핵심 기능 재검증
- 원인과 재발 방지 조치 기록

## 7. 무엇부터 준비할지 판단하는 기준

모든 것을 한 번에 만들 필요는 없다. 다음 질문으로 우선순위를 정한다.

1. 문제가 생기면 개인정보나 전체 데이터가 노출·삭제되는가?
2. 사용자가 핵심 기능을 전혀 쓸 수 없게 되는가?
3. 지금은 문제를 발견할 방법이 있는가?
4. 복구 방법을 실제로 시험했는가?
5. 다른 서비스나 수작업으로 임시 대응할 수 있는가?

개인정보 유출, 관리자 탈취, 데이터 복구 불능은 발생 가능성이 낮아 보여도 피해가 커서 먼저 준비한다. 사소한 디자인 오류나 편의 기능은 그다음이다.

## 10. 이 문서를 읽고 결정해야 할 것

- 장애와 백업 실패 알림을 어디에서 받을 것인가
- 서비스 복구에 허용할 데이터 손실 시간과 복구 시간은 어느 정도인가
- Storage 이미지까지 별도 백업할 것인가
- 백업을 어느 외부 저장소에 복사할 것인가
- 사용자 문의와 데이터·이미지 삭제 요청을 어떤 대장으로 관리할 것인가
- 매주 또는 매월 운영 점검에 실제로 쓸 수 있는 시간은 얼마인가

이 결정이 끝나면 페스티봄 상황에 맞는 실행형 운영 매뉴얼을 만들 수 있다.
