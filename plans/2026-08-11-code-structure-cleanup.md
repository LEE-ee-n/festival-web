# [완료] 2026-08-11 코드 구조 1차 정리

## 목적과 완료 조건

Festibom의 현재 기능과 데이터 흐름을 유지하면서 다음 문제를 단계적으로 줄인다.

1. 실수로 생성된 파일과 사용 여부가 불분명한 레거시 경로를 정리한다.
2. 한 페이지가 조회·상태·검증·저장·화면 렌더링을 모두 담당하는 구조를 역할별로 분리한다.
3. 여러 화면에 복사된 작은 표시·변환 로직을 공통 구현으로 모은다.
4. 신규 페스티벌 등록과 기존 페스티벌 수정의 저장 흐름은 계속 분리한다.

완료 조건:

- 정리 대상 파일의 역할과 의존 방향이 문서와 코드에서 일치한다.
- 페이지 컴포넌트는 화면 조립과 최상위 흐름 선택을 중심으로 담당한다.
- DB 조회·변경, 복잡한 상태 전이와 검증은 훅 또는 `lib` 모듈에서 담당한다.
- 같은 목적의 표시 컴포넌트와 안전한 변환 함수가 중복되지 않는다.
- 기존 신규 등록·기존 수정·아티스트 관리·개인 기록·달력 동작에 회귀가 없다.

## 정리 원칙

- 줄 수만 줄이기 위해 의미 없는 작은 컴포넌트를 만들지 않는다.
- 다음 중 하나에 해당할 때만 분리한다.
  - 독립적으로 테스트할 수 있는 계산·검증 로직
  - 조회·저장 등 외부 상태를 다루는 로직
  - 두 곳 이상에서 실제로 재사용하는 표시 로직
  - 한 파일에서 서로 다른 사용자 작업을 담당하는 화면 영역
- 신규 등록과 기존 수정은 공통 필드·검증·표시만 공유하고 controller와 저장 함수는 합치지 않는다.
- 기존 공통 함수·컴포넌트가 있으면 새로 만들기보다 확장한다.
- `any`를 추가하지 않는다.
- 파일 이동과 동작 변경을 같은 작업 묶음에서 함께 하지 않는다.
- 자동 삭제나 레거시 경로 삭제는 사용 여부 확인과 사용자 결정을 거친다.
- 티켓 사이트 크롤링 결과 검토·후보 저장과 티켓 정보를 포함한 기존 축제 JSON 업데이트 기능은 운영 도구로 유지한다.

## 확정 범위

### 1. 저장소 위생

- 루트의 `tatus --short` 파일은 Git 명령 출력이 저장된 실수 파일로 확인됐다.
- 구현 승인 후 정확한 파일을 다시 확인하고 삭제한다.
- `.env*`, `.next`, 캐시, 로그와 실행 데이터는 읽거나 수정하거나 커밋하지 않는다.

### 2. 관리자 신규 등록

대상:

- `app/admin/festival-candidates/page.tsx` 약 750줄
- `app/admin/festival-candidates/components/FestivalCandidateJsonUploader.tsx` 약 679줄

분리 방향:

- 후보 선택·초안 초기화·검증·매칭·단계 이동·승인·삭제를 신규 등록 전용 controller 훅으로 분리한다.
- 페이지는 작업함, 업로더, 단계별 검토 화면을 조립한다.
- JSON 업로더는 다음 역할로 나눈다.
  - 파일 읽기와 형식 검사
  - 기존 후보·정식 축제 일치 조회
  - 병합 선택 상태
  - 차이 검토 표시
  - 최종 후보 저장
- 승인 RPC와 임시 이미지 정리 순서는 변경하지 않는다.

### 3. 관리자 기존 수정

대상:

- `app/admin/festivals/import-json/page.tsx` 약 592줄
- `app/admin/festivals/import-json/StagedFestivalUpdate.tsx` 약 541줄

분리 방향:

- 라우트 진입과 `festivalId`, `updateDraftId` 해석은 페이지에 남긴다.
- 기존 수정 초안 조회·선택 상태·매칭·임시저장·삭제·최종 반영을 기존 수정 전용 controller 훅으로 분리한다.
- 단계 헤더, 최종 확인, 비교 결과와 작업 버튼 영역을 역할별 화면 컴포넌트로 분리한다.
- `LegacyFestivalJsonUpdateContent`는 레거시 경로 결정 전까지 현재 동작을 유지하거나 별도 파일로 격리한다.
- `/admin/festivals/import-json` 라우트와 `StagedFestivalUpdate`는 현재 기존 축제 수정 흐름이므로 삭제·차단하지 않는다.
- 직접 파일을 올리는 `LegacyFestivalJsonUpdateContent`도 티켓 정보를 포함한 전체 축제 JSON 수동 업데이트에 재사용할 수 있으므로 기능을 유지하고 파일만 분리한다.
- 신규 등록 controller와 기존 수정 controller는 합치지 않는다.

### 3-1. 티켓 사이트 크롤링 결과 수입

보존 대상:

- `app/admin/festival-candidates/components/TicketDiscoveryUploader.tsx`
- `lib/festivals/ticketDiscovery.ts`
- 티켓 크롤러가 생성하는 `ticket-discovery` JSON과 `festival_candidates` 저장 흐름

정리 원칙:

- 크롤링 보고서 `{ items: [...] }`를 검토·분류해 신규 후보로 저장하는 기능을 유지한다.
- 전체 축제 초안 `FestivalDraftJson`을 기존 축제에 반영하는 `import-json` 흐름과 입력 형식을 합치지 않는다.
- 추후 티켓 크롤링 결과 활용 범위를 넓힐 수 있도록 삭제·레거시 격리 대상에서 제외한다.

### 4. 관리자 페스티벌 기본정보·아티스트 관리

대상:

- `app/admin/festivals/[id]/lineup/hooks/useFestivalBasicInfo.ts` 약 392줄, `useState` 27개
- `app/admin/artists/page.tsx` 약 571줄, `useState` 15개

분리 방향:

- 기본정보 훅은 `기본정보 초안 / 썸네일 작업 / 저장 상태`를 구분한다.
- 서로 함께 저장되는 기본정보 필드는 하나의 명시적 draft 상태로 묶는 방안을 우선 검토한다.
- 아티스트 페이지는 다음 흐름을 분리한다.
  - 신규 아티스트 검색·등록
  - 전체 목록 조회·정렬·필터
  - 기존 아티스트 편집·이미지 업로드·삭제
- 현재 아티스트 표·편집 필드 컴포넌트는 재사용한다.

### 5. 개인 일기·페스티벌 기록 데이터

대상:

- `lib/diaries/festivalDiaries.ts` 약 341줄

분리 방향:

- `festivalDiaries.ts`: 일기 조회·저장·삭제
- `festivalRecordOptions.ts`: 기록 작성용 축제·라인업 조회
- `festivalRecords.ts`: 페스티벌 기록·아티스트 기록 저장과 상세 조회
- `festivalRecordTypes.ts`: 여러 화면에서 공유하는 기록 타입
- 기존 훅과 컴포넌트의 import만 단계적으로 변경하고 DB 쿼리 내용은 바꾸지 않는다.

### 6. 달력 controller 정리

대상:

- `components/Calendar.tsx` 약 453줄

분리 방향:

- 이미 분리된 달력 표시 컴포넌트는 그대로 유지한다.
- URL 쿼리·표시 월·뒤로가기 동기화와 축제 조회·선택 상태를 별도 훅 후보로 검토한다.
- 월 이동, PC 휠, 모바일 스와이프, 검색 선택과 지역 필터가 서로 의존하므로 앞 단계 완료 후 별도 작업으로 진행한다.

### 7. 작은 중복

검토 대상:

- Supabase 관계가 배열 또는 단일 객체로 오는 값을 정리하는 `firstRelation`
- 모바일 표 라벨 `MobileLabel`
- 관리자 CSV 수입 화면의 `formatFestivalPeriod`
- 화면별 Supabase 오류 문구 변환
- 신규·기존 기본정보의 `normalized_name` 입력·중복 확인 표시
- 후보 병합 화면과 기존 수정 비교표의 상태 라벨·색상 메타데이터

공통화 기준:

- 저장·승인 판단은 공유하지 않는다.
- 표시와 안전한 값 변환만 공통화한다.
- 사용처가 두 곳뿐이고 코드가 매우 짧으면 파일 추가 이득을 다시 판단한다.

## 레거시 경로 결정 필요

현재 관리자 메인에서 직접 연결되지 않는 경로:

- `app/admin/import/page.tsx`: XLSX 축제·출연진 통합 등록
- `app/admin/festivals/import/page.tsx`: CSV 라인업 등록
- `app/admin/festivals/new/page.tsx`: 과거 직접 신규 등록

각 경로는 구현 전에 다음 중 하나로 사용자가 결정한다.

- `유지`: 운영 도구로 문서화하고 관리자 화면에서 접근 경로를 명확히 한다.
- `격리`: `legacy` 폴더 또는 별도 문서에 보관하고 신규 코드가 의존하지 않게 한다.
- `삭제`: 참조·운영 사용 이력·대체 흐름을 확인한 뒤 관련 코드와 문서를 함께 제거한다.

레거시 경로는 이번 계획만으로 자동 삭제하지 않는다.

`app/admin/festivals/import-json/page.tsx`와 내부 직접 JSON 업로드 기능은 보존 대상으로 확정했다. 페이지 비대화를 줄이기 위한 파일 분리만 진행한다.

## 예상 데이터 흐름

관리자 화면은 다음 의존 방향을 사용한다.

1. `page.tsx`: URL과 최상위 화면 조립
2. 기능 전용 controller 훅: 로딩·상태 전이·사용자 작업 처리
3. `lib` 서비스: Supabase 조회·RPC·검증·결과 변환
4. 표시 컴포넌트: props와 callback으로만 동작

표시 컴포넌트가 Supabase를 직접 호출하거나, `lib` 서비스가 화면 상태를 알도록 만들지 않는다.

## 작업 순서

### 묶음 A — 저장소 위생·레거시 판단

1. 작업 시작 시 Git 상태와 정확한 삭제 대상을 확인한다.
2. `tatus --short`를 삭제하고 Git 상태에서 사라졌는지 확인한다.
3. 나머지 세 레거시 경로의 코드 참조, 관리자 접근 경로와 실제 운영 사용 여부를 확인한다.
4. 사용자에게 경로별 `유지 / 격리 / 삭제` 결정을 받는다.
5. 결정 결과를 `ARCHITECTURE.md`와 이 계획 문서에 기록한다.

### 묶음 B — 기존 수정 라우트와 레거시 분리

1. `import-json/page.tsx`에서 라우트 선택과 직접 JSON 업로드 구현을 파일 단위로 분리하되 두 기능을 모두 유지한다.
2. 공통 `firstRelation` 후보를 안전한 변환 함수로 분리한다.
3. 동작 변경 없이 관련 테스트·타입 검사·화면을 확인한다.

### 묶음 C — 신규 등록 작업함과 JSON 업로더

1. 신규 등록 controller 경계를 먼저 정의한다.
2. 페이지의 작업 함수들을 controller로 옮기고 화면 props를 정리한다.
3. JSON 업로더의 조회·병합 상태와 비교 UI를 분리한다.
4. 신규 등록 전체 5단계를 실제 후보로 회귀 확인한다.

### 묶음 D — 기존 수정 controller

1. `StagedFestivalUpdate`의 조회와 상태 초기화를 전용 훅으로 분리한다.
2. 임시저장·삭제·단계 이동·최종 반영을 훅으로 이동한다.
3. 단계별 화면을 분리하되 신규 등록 저장 흐름과 합치지 않는다.
4. 기존 수정 5단계와 최종 원자 반영을 회귀 확인한다.

### 묶음 E — 기본정보와 아티스트 관리

1. `useFestivalBasicInfo` 상태를 도메인별로 묶고 저장 payload가 동일한지 테스트한다.
2. 아티스트 신규 등록과 기존 편집 controller를 분리한다.
3. 이미지 업로드 실패 시 복원과 삭제 흐름을 실제 파일로 확인한다.

### 묶음 F — 개인 기록 데이터 모듈

1. 타입을 먼저 분리하고 기존 import를 변경한다.
2. 일기 CRUD, 기록 선택지, 기록 저장·상세 조회를 파일별로 이동한다.
3. DB 쿼리 문자열과 RPC 인수는 변경 전후 비교한다.
4. 일기와 페스티벌 기록 전체 흐름을 회귀 확인한다.

### 묶음 G — 작은 중복과 달력

1. 실제 중복 사용처가 유지되는 항목만 공통화한다.
2. 달력은 controller 훅 분리를 별도 계획으로 다시 검토한다.
3. 불필요한 추상화가 생기면 공통화하지 않는다.

각 묶음은 가능한 한 200~400줄 수준의 검토 가능한 변경으로 나누며, 한 묶음의 검증이 끝나기 전에 다음 묶음을 시작하지 않는다.

## 회귀 위험

- 파일 이동 중 이벤트 handler나 상태 초기화 순서가 달라질 수 있다.
- controller 훅 분리 중 stale state 또는 잘못된 effect dependency가 생길 수 있다.
- 신규 등록과 기존 수정의 유사 코드를 과도하게 합치면 서로 다른 승인 규칙이 섞일 수 있다.
- 레거시 경로를 삭제하면 문서에 없는 수동 운영 작업이 중단될 수 있다.
- 타입 이동 중 순환 import가 생길 수 있다.
- Supabase 관계 변환 공통화가 배열·단일 객체·NULL 사례를 잘못 처리할 수 있다.
