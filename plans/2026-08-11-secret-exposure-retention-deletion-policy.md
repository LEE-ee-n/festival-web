# [완료] 2026-08-11 비밀정보 노출 검사·개인정보 보유 및 탈퇴 삭제 정책

## 목적과 완료 조건

Git 현재 파일·전체 이력과 운영 로그 코드에서 비밀정보 노출 여부를 확인하고, 현재 Google 로그인·개인 일정·페스티벌 기록 기능에 맞는 개인정보 보유 및 회원탈퇴 삭제 정책을 확정한다.

완료 조건:

- 실제 비밀값을 출력하지 않고 Git 현재 파일·전체 이력·GitHub 경고·로그 경로의 노출 여부를 보고한다.
- 발견된 비밀정보는 종류·노출 위치·영향·폐기 및 교체 필요 여부만 마스킹해서 기록한다.
- 처리 항목별 목적·저장 위치·보유 기간·탈퇴 시 처리와 외부 서비스 잔존 범위를 표로 확정한다.
- 개인정보처리방침의 과거 문구를 실제 회원 기능에 맞게 수정한다.
- 회원탈퇴 구현에 필요한 삭제 순서와 예외를 확정하고 별도 구현 계획의 입력으로 남긴다.

## 확정 범위

### 비밀정보 검사

- `.env*` 내용은 읽지 않고 Git 추적 여부와 무시 규칙만 확인한다.
- 현재 Git 추적 파일과 전체 커밋 이력을 비밀정보 탐지 도구의 마스킹 모드로 검사한다.
- Supabase·Discord·Google·Vercel·GitHub 토큰, 비밀번호, 개인키와 일반적인 고엔트로피 문자열 패턴을 검사한다.
- Discord Bot 로그 작성 코드를 검토하고, 존재하는 실행 로그는 원문을 출력하지 않는 탐지 방식만 사용한다.
- 연결 권한이 허용되면 GitHub Secret Scanning 경고도 확인한다.
- 실제 노출이 확인되면 파일에서 지우는 것만으로 끝내지 않고 해당 제공자에서 키 폐기·재발급을 우선한다.

### 권장 보유·삭제 정책안

- Auth 이메일·Google 식별정보, 프로필, 관심 축제·아티스트, 개인 일정, 페스티벌 기록·메모·곡·미디어 참조, 베타 이용권: 회원 유지 기간 동안 보유하고 탈퇴 완료 시 지체 없이 삭제한다.
- 문의·제보 이메일: 기존 방침대로 처리 완료일부터 최대 1년 보유한다.
- Festibom이 직접 보관하는 접속·오류·보안 로그: 필요한 항목만 최대 90일 보유하는 것을 기본안으로 한다. 실제 저장하지 않는 공급자 로그는 공급자 설정의 실제 기간을 확인해 기재한다.
- 관리자 감사 로그: 운영 무결성과 보안 추적 목적의 보유 기간을 별도로 확인하며, 일반 회원 탈퇴 데이터와 연결되는 값은 삭제 또는 비식별화한다.
- DB 백업: 정상 서비스에서 조회하지 않고 재해 복구에만 사용하며, 공급자 백업 만료 주기에 따라 순차 삭제된다는 점을 방침에 명시한다.
- 법령상 별도 보존 의무가 생기는 결제·거래 데이터는 현재 무료 베타 범위에 포함하지 않고 유료화 계획에서 분리 보관 기간을 정한다.

## 제외 범위

- 이번 계획 승인 전 비밀키 폐기·재발급 또는 Git 이력 재작성
- 회원탈퇴 UI·서버 API·DB 함수의 실제 구현
- 결제·주문·환불 데이터의 보유 기간 확정
- 외부 서비스 대시보드 설정을 확인하지 않은 상태에서 보유 기간을 임의로 단정하는 것
- 법률 전문가의 공식 자문을 받은 것으로 간주하는 것

## 예상 수정 파일·데이터 흐름

- `app/privacy/page.tsx`
- 필요 시 `app/terms/page.tsx`
- `SECURITY.md`
- `PROJECT_STATUS.md`
- 이 계획 문서
- 검사 자동화를 승인하는 경우 `.github/workflows/*` 또는 `package.json`은 별도 범위로 계획한다.

탈퇴 정책상 삭제 순서:

1. 본인 재인증과 탈퇴 의사 확인
2. 사용자 소유 Storage 객체 확인·삭제
3. 활성 세션 및 갱신 토큰 폐기
4. `auth.users` 계정 삭제
5. `on delete cascade`로 프로필·관심·일정·기록·이용권 삭제 확인
6. 하위 공연·곡·미디어 참조 삭제 확인
7. 외부 분석 데이터와 백업의 제한·잔존 기간 안내

Supabase 공식 문서상 Auth 사용자 삭제만으로 기존 JWT가 즉시 무효화되지 않고, 사용자가 소유한 Storage 객체가 있으면 Auth 사용자 삭제가 실패할 수 있으므로 Storage와 세션을 먼저 처리한다.

## 작업 순서

1. 사용자 승인 후 마스킹된 비밀정보 검사를 현재 파일과 전체 Git 이력에 실행한다.
2. GitHub Secret Scanning 경고와 `.gitignore`, Bot 로그·예외 로깅 코드의 비밀값 포함 가능성을 대조한다.
3. 발견 항목을 `즉시 교체 / 코드 수정 / 오탐 / 이상 없음`으로 분류해 먼저 보고한다.
4. DB의 사용자 연결 FK와 Storage·외부 미디어 참조를 데이터 흐름표로 정리한다.
5. Vercel·Supabase·GA4·Clarity의 실제 보유 설정을 확인 가능한 범위에서 확인한다.
6. 위 권장 보유 기간 중 운영자 확인이 필요한 값을 확정한다.
7. 개인정보처리방침과 보안·현황 문서를 실제 처리 방식에 맞게 수정한다.
8. 문구·링크·TypeScript·ESLint·프로덕션 빌드와 배포 화면을 검증한다.
9. 회원탈퇴 기능은 확정된 삭제 정책을 기준으로 별도 구현 계획을 작성해 승인받는다.

## 회귀 위험과 검증 방법

- 검사 결과에 비밀값 자체가 노출될 위험: 모든 탐지는 redaction을 사용하고 보고서에는 종류와 위치만 남긴다.
- 과거 Git 노출을 현재 파일 삭제만으로 해결했다고 오판할 위험: 전체 이력 검사와 제공자 키 교체 여부를 분리해 확인한다.
- Auth만 삭제되고 Storage가 남거나 Auth 삭제가 실패할 위험: Storage 소유 객체를 먼저 처리하고 삭제 후 각 테이블의 잔존 행을 시험한다.
- JWT가 만료 전까지 유효할 위험: 탈퇴 전에 세션을 폐기하고 민감 작업에서 세션 유효성 확인 방식을 검토한다.
- 정책 문구와 실제 공급자 설정 불일치 위험: 대시보드 또는 공식 문서에서 확인하지 못한 기간은 확정값으로 쓰지 않는다.
- 다른 작업과 파일 충돌 위험: 현재 변경 중인 `PROJECT_STATUS.md`, `SECURITY.md` 등은 다른 작업 완료 후 최신 내용을 다시 읽고 최소 범위로 병합한다.
