# [운영 DB 적용 완료·화면 검증 대기] 베타 이용권·가입자 관리

## 목적과 완료 조건

관리자가 가입 회원을 확인하고 최대 20명에게 베타 이용권을 수동 부여·회수한다. 모든 로그인 회원은 마이페이지와 본인 데이터를 읽을 수 있지만 활성 이용권 회원만 개인 기능을 실행할 수 있다.

## 확정 범위와 제외 범위

- 관리자 회원 목록, 가입 순번, 가입일, 이용권 상태, 부여 순번 표시
- 활성 인원 `현재 / 20명` 표시와 수동 부여·회수
- 공통 이용권 상태 공급자를 통한 UI 일괄 제어
- 관심 아티스트, 공연 일정, 페스티봄 일기, 일정 이미지 실행 제한
- 기존 개인 데이터 조회 유지 및 이용권 회수 시 데이터 보존
- RLS와 저장 RPC에서 직접 요청 차단
- 실제 결제·환불·구독·만료 알림은 제외

## 예상 수정 파일·데이터 흐름

- `supabase/migrations/066_beta_access_entitlement.sql`
- `lib/supabase/database.types.ts`
- `lib/access/*`, `components/access/*`
- `app/layout.tsx`, 개인 기능 진입 컴포넌트와 훅
- `app/admin/users/page.tsx`, `components/admin/UserAccessManagement.tsx`, `app/admin/page.tsx`
- `DATABASE.md`, `PROJECT_STATUS.md`

로그인 → 공통 이용권 조회 → 화면은 조회 가능 → 실행 버튼은 이용권 상태로 제어 → 모든 DB 변경은 같은 활성 이용권 함수를 재검사한다.

## 작업 순서

1. [완료] 이용권 테이블, 공통 판별 함수, 관리자 RPC와 20명 제한을 작성한다.
2. [완료] 개인 데이터 변경 테이블에 중앙 이용권 트리거를 적용한다.
3. [완료] 공통 이용권 공급자와 잠금 안내를 구현한다.
4. [완료] 관리자 회원 목록과 권한 부여·회수 화면을 구현한다.
5. [완료] 개인 기능 버튼·작성 화면·일정 이미지에 공통 상태를 연결한다.
6. [부분 완료] 전체 테스트 258개, 타입 검사와 관련 린트는 통과했다. 로그인 화면은 로컬 Supabase 환경변수 미인식으로 확인하지 못했다.
7. [완료] 사용자가 운영 DB에 migration `066`을 적용했고 SQL Editor 성공 결과를 확인했다.

## 회귀 위험과 검증 방법

- UI 우회 위험: 이용권 없는 계정의 직접 INSERT·UPDATE·DELETE와 저장 RPC가 실패하는지 확인한다.
- 조회 차단 위험: 이용권 회수 후 기존 관심·일정·일기를 계속 읽을 수 있는지 확인한다.
- 개인정보 노출 위험: 비관리자가 회원 목록 RPC를 실행하지 못하는지 확인한다.
- 역할 혼동 위험: 베타 이용권 회원이 `/admin`에 접근할 수 없는지 확인한다.
- 정원 초과 위험: 관리자 RPC가 트랜잭션 잠금 안에서 20명 초과를 차단하는지 확인한다.

## 후속 개선점

- 결제 주문·구독·환불과 결제 웹훅
- 기간제 이용권과 자동 만료
- 관리자 화면에서 베타 정원 변경
- 이용권 변경 감사 이력 상세 화면

## 실제 결과

- 관리자 `/admin/users`에서 가입자와 가입 순번, 가입일, 베타 이용권 상태와 부여 순번을 조회하도록 구현했다.
- 관리자 전용 RPC로 수동 부여·회수하고 활성 베타 이용권을 최대 20명으로 제한했다.
- 전역 이용권 공급자를 추가해 관심 아티스트, 공연 일정, 일기 작성·수정과 일정 이미지 기능을 같은 상태로 잠근다.
- 기존 개인 데이터 SELECT는 유지하고 7개 개인 데이터 테이블의 변경만 공통 DB 트리거로 차단한다.
- migration `066`은 사용자가 운영 DB에 적용했고 SQL Editor에서 성공 결과를 확인했다.
- 관리자 회원 목록과 실제 계정별 부여·회수·차단 동작은 화면 검증 대기다.
- 전체 테스트 258개, TypeScript와 관련 ESLint가 통과했다.
