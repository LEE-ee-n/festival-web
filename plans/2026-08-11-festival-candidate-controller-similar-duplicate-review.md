# [완료] 2026-08-11 신규 축제 controller 분리·유사 중복 검토

## 목적과 완료 조건

신규 축제 등록 페이지의 상태·처리 흐름을 controller 훅으로 분리하고, 정확 식별값이 다르더라도 같은 연도와 유사한 이름을 가진 기존 축제를 관리자 확인 없이 신규 등록하지 못하게 한다.

완료 조건:

- 신규 등록 페이지는 화면 조립을 중심으로 하고 후보 선택·저장·단계 이동·승인·삭제는 전용 controller가 담당한다.
- 축제 판정은 `완전 일치 / 유사 후보 / 신규` 세 상태를 사용한다.
- 유사 후보가 있으면 관리자 선택 전 신규 최종 승인이 불가능하다.
- 관리자는 유사 후보를 보고 `기존 축제 수정으로 전환` 또는 `별도 신규 축제로 등록`을 선택할 수 있다.
- Bot, JSON 업로드, 티켓 discovery와 직접 작성 후보가 같은 판정 함수를 사용한다.
- 승인 직전 최신 승인 축제를 다시 조회해 후보 생성 이후 생긴 중복도 확인한다.

## 확인된 현재 원인

- 현재 자동 기존 판정은 `normalized_name + start_date + end_date` 완전 일치만 허용한다.
- 완전 일치가 없으면 표시명과 `search_aliases`가 매우 비슷해도 바로 `new`가 된다.
- Bot 테스트에도 `유사한 표시명은 exact identity를 대체하지 않고 new`라는 기존 규칙이 명시돼 있다.
- DB 최종 승인 RPC는 완전 일치 중복만 차단하므로 이름이 조금 다른 동일 행사는 삽입될 수 있다.

## 확정 범위

### 1. 신규 등록 controller

- `app/admin/festival-candidates/page.tsx`에서 다음 흐름을 `useFestivalCandidateController`로 분리한다.
  - 후보 선택과 초안 초기화
  - 아티스트 자동 매칭
  - 초안 검증·임시저장
  - 단계 이동과 오류 위치 이동
  - 최종 승인·임시 이미지 정리
  - 후보 삭제와 직접 작성 생성
- `useFestivalCandidateDraft`와 `useFestivalCandidates`는 현재 역할을 유지하고 controller가 두 훅을 조합한다.
- 페이지는 필터·목록·단계 탭과 작업 버튼을 조립한다.

### 2. 축제 유사 판정

판정 순서:

1. `normalized_name + 시작일 + 종료일` 완전 일치 한 건이면 `기존 축제 수정`이다.
2. 식별값이 누락됐거나 완전 일치가 복수면 `판별 확인 필요`다.
3. 완전 일치가 없으면 시작일의 연도가 같은 승인 축제만 유사 비교 후보로 삼는다.
4. 들어온 축제명·`normalized_name`과 기존 축제의 표시명·`normalized_name`·`search_aliases`를 정리해 가장 높은 이름 유사도를 계산한다.
5. 기준 이상이면 `유사 축제 후보`, 없으면 `신규`다.

권장 초기 기준:

- 같은 시작 연도 필수
- 정리한 이름의 완전 일치 또는 상호 포함은 유사 후보
- 그 외 문자열 유사도 50% 이상은 유사 후보
- 날짜가 완전히 같으면 유사 판정 사유에서 강하게 표시하되 자동 병합하지 않음
- 점수와 판정 사유를 관리자에게 표시

유사 판정은 중복을 자동 확정하는 규칙이 아니라 관리자 확인을 강제하는 안전장치이므로 일부 과잉 탐지를 허용한다.

### 3. 관리자 판정 UI

- 후보 상단에 유사 축제 목록을 유사도·연도·전체 기간과 함께 표시한다.
- `기존 축제 수정으로 전환`: 선택한 기존 축제 ID와 현재 초안을 기존 수정 작업함으로 넘긴다.
- `별도 신규 축제로 등록`: 관리자가 유사 후보를 확인했다는 결정을 후보의 `comparison_json`에 저장한다.
- 이름·연도·기간이 바뀌면 기존 확인 결정을 무효화하고 다시 판정한다.
- 확인되지 않은 유사 후보가 있으면 5단계 최종 승인 버튼을 차단한다.

### 4. 최종 승인 안전장치

- 최종 승인 직전에 승인 축제 목록을 다시 조회하고 같은 판정 함수를 실행한다.
- 새 유사 후보가 생기거나 확인 당시 입력값이 바뀌면 저장하지 않고 다시 확인하도록 한다.
- 완전 일치 중복을 막는 기존 DB 검사와 고유 인덱스는 유지한다.
- 유사 후보를 확인하지 않은 상태에서는 승인 RPC를 호출하지 않는다.

## 실제 결과

- 신규 등록 페이지의 상태·처리 흐름을 `useFestivalCandidateController`로 분리했다.

- 이름·날짜 변경 시 확인을 무효화하고 승인 직전 최신 승인 축제로 다시 검사한다.
- 웹 테스트 273개, Bot 테스트 32개, 전체 ESLint, TypeScript, `git diff --check`를 통과했다.
- 로그인된 관리자 localhost 화면 확인은 남아 있다.

## 회귀 위험

- 기준이 낮으면 다른 축제가 과도하게 유사 후보로 표시될 수 있다.
- 기준이 높으면 철자 오류가 큰 중복을 놓칠 수 있다.
- 같은 이름의 연례 축제를 이전 연도 행사와 잘못 연결하면 안 된다.
- 후보 확인 후 축제명이나 날짜를 수정했는데 과거 확인 상태가 남으면 안 된다.
- 기존 수정 전환 중 신규 후보와 수정 초안이 동시에 남을 수 있다.
- controller 분리 중 단계 이동·초안 초기화·오류 포커스 순서가 달라질 수 있다.

## 검증 방법

- 완전 일치 → 기존 수정
- 같은 연도·동일 날짜·이름 표기 차이 → 유사 후보
- 같은 연도·비슷한 이름·다른 날짜 → 유사 후보
- 다른 연도·같은 이름 → 신규
- 같은 연도·전혀 다른 이름 → 신규
- 이름·날짜 수정 후 기존 확인 무효화
- 유사 후보 미확인 상태의 최종 승인 차단
- 기존 축제 선택 시 수정 작업함 생성과 신규 후보 중복 잔존 여부 확인
- 전체 웹 테스트, Bot 테스트, 타입 검사, ESLint, `git diff --check`
- localhost에서 직접 작성·JSON 업로드·티켓 discovery·Bot 후보의 실제 판정 화면 확인

## 확정된 사용자 결정

- 이름 유사도 초기 기준은 `50%`로 적용한다.
- 이름이 서로 완전히 포함되면 유사도 점수와 관계없이 유사 후보로 판정한다.
- 유사 후보 확인 시 `기존 축제 수정으로 전환 / 별도 신규 축제로 등록` 두 선택을 모두 제공한다.
- 실제 운영 사례를 확인한 뒤 임계값 상수만 다시 조정할 수 있게 구현한다.

## 후속 개선점

- 운영 사례가 쌓이면 실제 오탐·누락을 기록해 유사도 기준을 조정한다.
- 필요하면 장소와 월·일 근접도를 보조 점수로 추가하되 자동 판정 기준으로 사용하지 않는다.
- 과거 중복 2~3건은 자동 병합하지 않고 별도 데이터 정리 계획으로 처리한다.
