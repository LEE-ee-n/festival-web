# 페스티벌 삭제와 승인 이력 연결 해제

상태: 코드 구현 완료 · 운영 DB 적용 및 실제 삭제 확인 대기

## 목적과 완료 조건

- 승인 이력이 연결된 페스티벌도 관리자 화면에서 정상 삭제할 수 있게 한다.
- 페스티벌 삭제 후 승인 이력은 보존하고 `festival_id`만 `NULL`로 만든다.
- 승인 완료 이력의 나머지 내용은 계속 수정할 수 없게 유지한다.
- 삭제 성공 시 기존 감사 로그에 관리자·시각·페스티벌명·삭제 전 축제 정보를 남긴다.

## 확정 범위

- 승인 이력 잠금 트리거에서 삭제에 따른 `festival_id: 기존 ID → NULL` 변경만 허용한다.
- `festival_id`와 자동 갱신 시각을 제외한 다른 값이 함께 바뀌면 계속 차단한다.
- 페스티벌 목록 화면에서 Supabase의 실제 오류 메시지를 표시한다.
- 라인업과 티켓은 기존 외래키 `ON DELETE CASCADE` 동작을 유지한다.

## 제외 범위

- 라인업·티켓 각각의 삭제 감사 로그
- 승인 이력 삭제
- 삭제된 페스티벌 복원 기능
- ID 재사용

## 예상 수정 파일과 데이터 흐름

- `supabase/migrations/044_allow_candidate_unlink_on_festival_delete.sql`
  - 승인 이력 잠금 트리거의 예외 조건을 좁게 추가한다.
- `app/admin/festivals/page.tsx`
  - 일반 `Error`가 아닌 Supabase 오류 객체의 메시지도 표시한다.
- 필요 시 Supabase 오류 메시지 공통 함수와 단위 테스트를 추가한다.

삭제 흐름:

1. `delete_festival_with_audit`가 삭제 전 축제 정보를 감사 로그에 기록한다.
2. `festivals` 행을 삭제한다.
3. 라인업·티켓은 cascade로 삭제한다.
4. 승인 이력은 삭제하지 않고 외래키가 `festival_id`를 `NULL`로 바꾼다.
5. 잠금 트리거가 이 연결 해제만 허용하고 다른 변경은 차단한다.

## 회귀 위험과 검증

- 승인 이력의 상태·원문·제목 수정이 여전히 실패하는지 확인한다.
- 승인 이력이 연결된 테스트 축제를 삭제해 성공 여부를 확인한다.
- 삭제 후 승인 이력 행은 남고 `festival_id`만 `NULL`인지 확인한다.
- 삭제 감사 로그에 축제명과 삭제 전 데이터가 남는지 확인한다.
- 변경 파일 린트·타입 검사와 migration SQL 검토를 수행한다.

## 후속 개선점

- 필요하면 삭제 확인창에 승인 이력 보존 안내를 추가한다.
